# Contributing to Awesome Everything-as-Code

Thank you for your interest in contributing! This document provides guidelines for contributing to this curated list.

## How to Contribute

1. **Fork the repository** and create a new branch for your contribution
2. **Add your tool** to the appropriate category in README.md
3. **Submit a pull request** with a clear description of what you're adding

## Inclusion Criteria

To be included in this list, a tool or resource must embody the **"as Code"** philosophy:

### Required

- **Text-based**: Uses human-readable text files as the primary interface
- **Versionable**: Works seamlessly with Git version control
- **Declarative**: Describes *what* should exist, not *how* to create it
- **Functional**: Must be in a usable state with active development or stable release

### Preferred

- **Open Source**: Preference for OSI-approved open source licenses
- **Documentation**: Should have clear documentation explaining usage
- **Community**: Active community or adoption is a plus
- **Unique value**: Demonstrates clear benefits over existing alternatives

## Formatting Guidelines

### Entry Format

Each entry should follow this format:

```markdown
- [Tool Name](https://example.com/) - Brief description of what it does and why it's awesome.
```

### Style Rules

- **Alphabetical Order**: Tools within each category should be in alphabetical order
- **Description**: Keep descriptions concise (one sentence) ending with a period
- **Links**: Use the official project page or main GitHub repository
- **Capitalization**: Use proper capitalization as specified by the project

## Categories

Tools should be placed in the most appropriate "X as Code" category:

- **Infrastructure as Code**: Provisioning and managing cloud resources
- **Configuration as Code**: System and application configuration
- **Policy as Code**: Security, compliance, and governance rules
- **Diagrams as Code**: Creating visualizations from text
- **Data Transformation as Code**: ETL and data pipeline definitions

If a tool doesn't fit existing categories, propose a new category in your pull request.

## Adding Resources

When adding books, articles, or other resources:

- Ensure the content is high-quality and directly relevant to EaC
- Prefer official sources and well-established authors
- Include author names for books and articles
- Verify all links are working

## Pull Request Process

1. **Search first**: Check existing entries to avoid duplicates
2. **One tool per PR**: Submit separate PRs for unrelated additions
3. **Explain why**: Describe why the tool belongs in this list
4. **Follow formatting**: Ensure your entry matches the style guide
5. **Test links**: Verify all URLs work before submitting

## Quality Standards

We prioritize quality over quantity. Pull requests may be rejected if:

- The tool doesn't follow the "as Code" philosophy
- The description is unclear or promotional
- The project is abandoned or non-functional
- It duplicates an existing entry
- The formatting doesn't follow guidelines

## Questions?

Not sure if a tool fits? Open an issue for discussion before submitting a pull request.

## Code of Conduct

Please review our [Code of Conduct](code-of-conduct.md). Be respectful and constructive in all interactions.
